# Stage 43G-69：旧A方式・v2形式の長期保存実測比較

作成日：2026-10-12

## 目的

Stage 43G-67（旧A方式）とStage 43G-68（独立したv2架空方式）の**それぞれで実測した保存レポート**を、取り違え・二重集計・安易な性能比較を防ぎながら対比する。

過去記録の保存方針は引き続き **A方式：試合スコア・イニング別得点・個人成績**。元保存形式を変更せず、正式ゲームGUIも新設しない。

## 実装

実装：phase2_engine/career_cross_era_storage_evidence.py

- compare_independent_a_audits(legacy, v2) はStage 43G-67と68の完成済みJSONレポートだけを受け付ける。出典、監査実施フラグ、封印済みの年度、保存試合・学校・キャッシュ行数、年度別JSON容量、SQLite実容量の算術整合性を確認する。
- 旧A方式は1～9999年、v2は10000年以降のみ。重複・並べ替え、証拠フラグ欠損、原本SHAの非書込が証明されない報告、欠けた個人成績キャッシュ検証結果を拒否する。
- 各形式について年度数、試合数、学校年度ロスター数、cache選手年度数、実保存JSONの構成別バイト数、試合1件・ロスター1校年度・cache選手1年度あたりの**観測平均JSON量**を算出。
- 元のSQLファイルの合計容量も併記するが、**SQLiteの容量差をv2の削減効果と断定しない**。旧Aは3ファイル、v2は4ファイルであり、共通ロスターやcalendarの取り扱いが異なる。
- 旧Aには新規永久選手identityの年次JSON容量があり、v2の年度別監査にはidentityの年度帰属を含めないため、総容量の直接比較は行わない。
- 本APIは**完成済み実測レポートの照合**であり、元のSQLiteへ再アクセスしない。原本検証が必要なら先にStage 43G-67/68の各監査を実行する。
- 年2026と年10000のキャリア・試合・日付を連結しない。実試合の年度進行、全国3,000校×100年の実行結果を推測しない。

## 実行例

コマンド：

python -m phase2_engine.career_cross_era_storage_evidence --legacy-report build/reports/stage43g67_actual_legacy.json --v2-report build/reports/stage43g68_actual_v2.json --output-json build/reports/stage43g69_independent_compare.json

出力先に入力レポートと同じパスを指定した場合は上書きを拒否する。

## 実測条件と解釈

- Stage43G-67：2校、12年度、架空の完全A方式24試合。
- Stage43G-68：2校、12年度、独立した架空v2形式23試合。
- サンプル試合数が異なるため、総JSON容量の差をそのまま「形式移行による節約」とみなさない。
- SQLite物理容量はページ、インデックス、空き領域、calendar、共有ロスターの影響を含み、サンプルを線形に全国規模へ外挿しない。
- 読み取り時間も、旧Aは元試合と派生成績のサンプル、v2は年度全試合と学校ごとの深度原本検査と条件が異なる。速さの優劣を算定しない。
