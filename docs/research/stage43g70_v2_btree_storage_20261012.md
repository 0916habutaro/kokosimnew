# Stage 43G-70：保存容量の構成要素・v2の重複索引改善と読み取り専用監査

作成日：2026-10-12

## 目的

Stage43G-67〜69の保存容量比較から、試合原本・学校ロスター・派生成績キャッシュに加えて、SQLiteの索引B-treeの実際の容量を切り分ける必要がある。本工程では、**保存フォーマットを変更せず安全に回避できる新規作成時の重複索引1件**を改善する。

試合結果のA方式（スコア・イニング別得点・個人成績）には変更を加えない。正式GUI・ゲーム進行・全国3000校×100年の連続プレイは対象外。

## 特定した構造

v2の試合記録 `v2_option_a_matches` には `PRIMARY KEY (year, competition_id, match_id)` があり、SQLiteが同じ3列の一意B-treeを自動的に用意する。一方、旧スキーマには、まったく同じ3列の独立した `idx_v2_games_school_a` が追加されていた。

これは主キーに対する完全重複索引であり、データの追加ごとに索引ページが別途割り当てられる可能性がある。

- **新規v2アーカイブ**：重複している `idx_v2_games_school_a` の CREATE INDEX 文だけを廃止。必須の主キー、自動一意索引、ゲーム日別の `idx_v2_games_day` は保持する。
- **既存v2アーカイブ**：変更しない。VACUUM・DROP INDEX・テーブル再構築・既存の試合やキャッシュ更新は行わない。旧索引が残っていても、そのまま読み取り可能。
- **日付・試合検索**：EXPLAIN QUERY PLANで、大会＋試合IDの主キーseekとゲーム日別の `idx_v2_games_day` のseekが成立することを確認する。

## 新規監査API

`phase2_engine/career_storage_btree_audit.py` の `audit_save_storage_btrees(slot_root)` は、既存のセーブスロットにある以下のファイルを監査する。

- 旧A試合原本 `historical_matches.sqlite3`（あれば）
- v2試合原本 `fictional_option_a_v2.sqlite3`（必須）
- v2カレンダー `sandbox_calendar_v2.sqlite3`（あれば）
- 共通学校ロスター `career_rosters.sqlite3`（あれば）
- 旧A派生成績 `derived_player_stats.sqlite3`（あれば）
- v2派生成績 `fictional_v2_player_stat_cache.sqlite3`（あれば）

元SQLiteは読み取り専用で開き、PRAGMAから利用中のインデックス・主キー自動索引・ファイルの実ページ数を取得する。SQLite環境で `dbstat` が使える場合は、B-tree名ごとの実割当ページバイト数を集計する。非対応の場合は「実索引ページ容量は未取得」と表示する。

**監査前後ですべての元SQLiteのSHA-256を比較**して原本不変を確認する。

実行例：

```bash
python -m phase2_engine.career_storage_btree_audit \
  --slot out/saves/EXAMPLE \
  --output-json build/reports/stage43g70_btrees.json
```

## 注意と証拠の限界

- この監査は**SQLiteの構造・実ファイル割当・SQL検索計画**を調べるものであり、元試合や選手成績の内容が真であることを証明しない。元の試合やcache SHA整合性は従来のStage43G-67/68側で検査する。
- v2の旧重複索引が存在する場合、`dbstat`でその索引に割り当てられたページ数を報告するが、**索引を削除した場合にその全量がファイルサイズから減るとは約束しない**。SQLiteのページ再利用・空きページ・VACUUMの有無によって変わる。
- JSONの実バイト、SQLite全ページ割当、索引B-tree割当の3つは別の指標。索引に使われるすべての容量をdbstatのデータだけで正確に分解したと主張しない。
- 旧Aファイルとv2ファイルを比べた場合の1試合容量差を、単純な「形式をv2に変更すれば容量が減る」と解釈しない。
- 将来の既存セーブに対する明示的な移行・最適化は別工程で、現在は**既存ファイルを絶対に更新しない**。

## 専用テスト

新規7件では、使い捨てのv2完全A記録を2試合保存して、新スキーマが不要索引を生成しないこと、主キーと日付検索に正しい索引が使われること、過去の旧索引が残ったデータも読み取り可能で更新されないことを確認する。

さらに旧A原本・v2カレンダー・共通ロスター・v2成績cacheを持つ一時セーブでファイル役割別の割当を計測し、SQLiteが元のファイルを変更していないことをSHA-256で確認する。

Stage43G-27/68、Python全unittest、関東8都県17校E2Eを回帰条件とする。

## 次工程

新規保存データだけで実際のファイル容量削減を比較し、旧A／v2の派生成績cacheで主キーとの重複インデックスがないかを追加監査する。もし既存セーブの索引削減を検討する場合は、明示的なバックアップとロールバック手順を設計してから行う。
