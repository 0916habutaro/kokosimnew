# Stage 43C：ライブセーブとA方式履歴SQLiteの連携・追記保護

更新日：2026-10-10
対象：ココシミュNew / Stage 43B（PR #131）以降
作業範囲：**同一年（現行2026年）の保存済みライブ試合を、セーブ枠固有のSQLiteへ増分追記**する。
非対象：翌年進行・年度ロールオーバー、正式GUI、全国大会の全試合で詳細GameStatsを保証すること。

## 1. 仕組み

```text
LiveGameService.play_today / next_day / advance_to / advance_through
        │（ゲームの進行）
        ▼
LiveSeasonRuntimeState：確定試合＋ability_detail
        │
        ├─ LiveGameService.save_game/autosave_game
        │      │
        │      ├─① SaveSlotManager：再実行可能なJSONセーブを保存
        │      └─② HistoricalMatchArchive：A方式履歴をSQLiteへ追記
        │
        └─ LiveGameService.load_game
               ├─ JSONを検証・再生
               └─ 履歴SQLiteへ不足していた確定試合を再同期
```

履歴DB：`<save_root>/<slot_id>/historical_matches.sqlite3`

- 同じセーブ枠の古いJSONバックアップを読み込んでも、履歴SQLiteに既にある後日の試合を削除しない。
- 同一の`(year, competition_id, match_id)`かつ内容が完全一致する場合は再登録しない。
- 同じキーの試合結果、選手成績やイニング得点が異なる場合は`HistoricalMatchConflictError`で**トランザクション全体を拒否**する。
- 別のシーズン計画／乱数seed／resolver契約を同じセーブ枠へ混ぜないよう`archive_identity`を保存して照合する。
- 一括処理の途中で不整合が見つかっても新規試合の部分追加をコミットしない。
- 通常の`BrowseRepository.replace_season_views`のような年単位DELETEを一切使用しない。

## 2. A方式の保存範囲

| 記録 | 履歴SQLite | 扱い |
|---|---|---|
| 大会・試合ID、試合日と根拠、ラウンド、対戦校 | `historical_matches` | 確定試合を全件保存 |
| スコア、勝者・敗者、結果出典 | 同上 | 勝敗と得点の食い違いは保存前に拒否 |
| イニング別得点・未実施の裏 | `payload_json.inning_scores` | Stage43B能力試合で生成済みのものだけを保存、旧記録には作らない |
| 安打・失策、打者／投手の試合別成績 | `payload_json.team_stats / batter_stats / pitcher_stats` | Stage43B能力試合で出力された場合にのみ保存 |
| 全打席イベント | **保存しない** | 一時試合結果内では使っても、長期記録には含めない |

- `payload_json`は正規化した不変スナップショット。SHA-256で同一性を検証。
- 日付・学校・大会の条件を指定できるSQLite複合索引を備える。
- `HistoricalMatchArchive.get_match()`および`list_matches(year, school_id, limit, offset)`で必要な試合だけ取り出せる。
- 現行の`BrowseRepository`（大会一覧・学校戦績等の参照データ）とは別の保存領域として扱う。既存の閲覧GUIへの統合は後続工程。
- 異なるゲームセーブ枠同士は別ファイルのため記録を混合しない。

## 3. 障害・復元の契約

セーブは **①JSON→②履歴SQLite** の順序とする。2ファイル間の単一トランザクションはない。

| 障害位置 | 結果 | 復旧 |
|---|---|---|
| JSONセーブ前に失敗 | 履歴SQLiteの新規書込みをしない | 既存セーブ／バックアップから継続 |
| JSONセーブ成功後にSQLite同期失敗 | JSONが先行し履歴に不足あり得る | 次回`load_game()`で確定試合の再生結果を照合して再同期。例外は握りつぶさず利用者へ返す |
| 既に同一試合がある | 不変の同一結果ならスキップ | 何度同期しても履歴行は増えない |
| 既存と異なる結果の再生 | 自動上書きを拒否 | 先にセーブ・生成条件の違いを調査。意図的な履歴破棄／再構築は専用操作として後日設計 |
| より古いバックアップをロード | 履歴の先行記録は維持 | 上書き・削除なし。以後の分岐試合で結果が変わった場合は衝突検出 |
| セーブ枠の削除 | 該当枠ディレクトリごと削除 | 履歴SQLiteも削除される。重要セーブはフォルダ単位でバックアップが必要 |

なお履歴SQLite単体が破損した場合、JSONの保存済み再生可能な範囲を超えて復元できる保証はない。**バックアップはセーブJSON・rolling backup・履歴SQLiteをセットで取得**する運用とする。SQLiteを自動的に消去して作り直す救済策は実装しない。

## 4. セーブと非セーブ操作の区別

- 通常の手動セーブ、オートセーブに合わせて履歴も追記する。
- `autosave=False`で進めた段階の新規試合は、まだ履歴SQLiteへ永続化しない。次回の明示的セーブ／オートセーブ時にまとめて追記する。
- `new_game(save_initial=False)`の場合も、初回の実際のセーブまで履歴アーカイブは書き込まない。
- `load_game`時の同期は、JSONチェックサム、計画fingerprint、試合結果の再生監査が成功した後のみ実行する。
- ロード対象が古いバックアップでも、履歴は遡って削除しない。

## 5. 検証・残件

追加テスト：
- A方式の得点・チーム・打者・投手データの読み出し
- 全打席イベントをDBから除外
- 冪等保存・衝突拒否・同一トランザクションでのロールバック
- 古いセーブの再同期でも未来の既存履歴を消さない
- 別seed／別計画との混同拒否
- generated_v1でイニング情報がないときに偽の記録を作らない
- ページ分割と学校ID指定の読取り
- JSON保存前失敗時のSQLite非更新

後続の重要課題：
1. Stage 43D：**2026→2027**の年度移行と、年度を跨いでセーブ枠／履歴のidentityを継続させる契約。現Stage 43Cでは保存計画を**同一年度に固定**しており、複数年プレイ完成とは扱わない。
2. 途中記録の完全性・既存履歴の破損検出を強化し、必要なバックアップ・リカバリをGUIから操作可能にする。
3. 年度毎の膨大な試合履歴を、必要に応じてデータ分割・圧縮しつつ閲覧可能にする。
4. `HistoricalMatchArchive`の個人成績JSONから年度・通算ランキング向けread modelを追加する。
5. 史実の二次資料とゲーム生成試合の分離、地方予選や合同チームの意味づけ、選手の年度跨ぎ継続を維持する。

**本実装はライブ保存と履歴SQLiteの最初の結合**である。全47都道府県の試合方式の正式網羅、年数無制限の進行、正式画面の完成を宣言しない。
