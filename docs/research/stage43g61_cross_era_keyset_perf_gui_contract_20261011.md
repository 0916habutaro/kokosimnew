# Stage 43G-61：長期履歴の主キーseek・読み取り実測・正式GUI接続前提

作成日：2026-10-11

## 位置付け

#202で導入した旧A方式（ISO日付）・独立v2（論理日付）の封印済み年度カタログを、何百年もの登録年を持つセーブでも一定件数ずつ閲覧できるようにする。

これは**保存年度候補一覧と実際のゲーム年度実行を分離する**ための開発。年10000の本番大会エンジン、全校100年分の実試合保存、正式ゲームGUIの実装は含まない。

## 変更した契約

### 年度候補の高速検索

従来の `page(limit, offset)` は互換APIとして維持。新たに `page_after(before_year=None, limit=24)` を実装。各SQLiteに

```sql
SELECT year FROM v2_game_years
WHERE status='sealed' AND year < :cursor
ORDER BY year DESC LIMIT :limit_plus_one;
```

のような主キー範囲検索を実行する。

- cursorは「この年度より古い」という**排他的な年整数**。初回はNone。古い方へのリンクだけを得るので既存OFFSETに依存しない。
- 応答は `years`、`has_older`、`next_cursor_before_year` を持つ。APIは最大24件を返し、内部では各形式最大25件の年度ヘッダだけ読む。
- 旧方式とv2の原本は別SQLiteのまま。データを移行、変換、ATTACHしない。
- 年度ヘッダは未検証の候補。試合閲覧では必ず従来のread gate（封印ledger、原本SHA、カレンダー、年度／学校ID）を通す。
- 不明年度を推定しない。旧方式とv2での時系列の合算やキャリア成績合算を許可しない。

### 計測CLI

```bash
python -m phase2_engine.career_cross_era_year_probe --slot out/saves/EXAMPLE --limit 24 --max-pages 50
```

既存セーブに保存された年度ヘッダの連続ページ読み込みで、1ページの実測時間（中央値）、tracemallocメモリ最大値、閲覧した年度数、上限内で最終ページまで到達したか、SQLiteファイルSHA不変をJSONで報告する。デフォルト50ページ、指定可能100ページまで。数値は当該環境／当該データの実測にすぎず本番ゲームの100年完走性能ではない。

### Tkinter試験GUIとの接続

既存 `CareerCrossEraGuiPilot` は変更せず、起動時に `--years saved --year-before <N>` を指定すればseek一覧から最大24年を取得できる。既存 `--years saved --year-page-offset N` も継続利用可能。これは*正式GUIの設計に引き渡せる読み取りAPI*であり、正式GUIそのものにはしない。

## テスト

- 2026年旧Aと10000年v2の保存fixtureに加え、**年10001〜11250の1250件のメタデータだけ**を使い捨てSQLiteに登録。試合や選手の年次生成はしない。
- 保存年度1252件（2026＋10000〜11250）が取りこぼしなく、重複なく、降順に51ページ以上で回収できることを確認。
- `EXPLAIN QUERY PLAN`で年整数主キーの検索計画を確認し、読み取り専用の計測結果と保存SQLiteのハッシュ不変を確認。
- 改ざんされたv2原本SHAは候補一覧の存在を妨げない一方、閲覧は拒否されることを確認。
- Stage43G-30〜32/60回帰、Python全unittest、関東E2Eをマージ条件とする。

## 制約・今後の正式GUI要件

- 非常に古い年度まで読み進める際のcursorは保存ヘッダの年度数値であってゲーム進行の時刻ではない。年度削除・再登録中の同時閲覧については整合性方針が必要。
- 現行Tk試験GUIは最大24年の選択表示。正式ゲームGUIでは年度検索・学校検索・進行操作・閲覧を分離し、選択する年度の原本検証失敗をユーザーに明示する。
- 100年、1000年の学校・選手データ容量／累積記録の生成と保存を含む大規模E2Eは未完了。実ゲーム進行性能とヘッダ一覧性能を混同しない。
