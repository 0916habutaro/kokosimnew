# ココシミュNew：閲覧機能全体仕様（Stage 42 初版）

更新日：2026-10-10  
管理対象：**試合結果・大会経過・学校・選手・記録を「眺める」ための閲覧機能**  
基準：`0916habutaro/kokosimnew` main（Stage 13E-3G-41 / PR #127 まで）

## 1. 文書の目的

ココシミュNewは高校野球の**選手育成よりも、実際の高校野球に沿った大会の進行・試合結果・個人成績・過去の記録を閲覧する**ことを中心にする。本書は、正式GUIを実装する前に「何が閲覧できればゲームとして成立するか」を幅広く記録する**機能の基準台帳**。Stage42は設計整理であり、正式GUIの製作やゲームエンジンの挙動変更を行わない。

機能候補・実装状況・仮の優先度・必要データ・参照先は、**`docs/design/viewing_feature_catalog_stage42.csv`** を正本とする。本書の集計値と画面例は当該CSVに対応する。対象は**71機能・13分類**。追加・統合・削除する際は機能IDを維持しながら台帳と関連ドキュメントを更新する。

関連文書：
- `docs/design/viewing_screen_navigation.md`：画面情報構造、画面間遷移、年度・学校・大会のID引継ぎ方針
- `docs/design/viewing_data_requirements.md`：画面に必要なデータ、保存・集計元、欠損・未確定・史実/生成の境界
- `docs/design/viewing_feature_catalog_stage42.csv`：71項目の機械可読台帳（機能ID、現状、仮優先度、必要データ、参照パス）
- `docs/design/player_stats_read_model.md`、`docs/design/player_master_gui_contract.md`、`docs/design/game_event_stats_contract.md`：既存の詳細契約

## 2. 機能の判定区分

| `current_state` | 日本語 | 判断基準 |
|---|---|---|
| `gui_prototype` | 簡易GUI試作あり | Stage12U/13D3等にTk画面と処理がある。正式ゲームGUI完成という意味ではない |
| `read_model_only` | 読取API・データ契約あり | Python read modelやSQLite queryには存在するが、専用画面の実装・接続は別途必要 |
| `preview_only` | 隔離試験プレビューに限定 | Stage34〜41等の架空例・2026広島秋西二次史実でのみ閲覧。全国共通の本番機能ではない |
| `design_only` | 詳細方針・契約のみ | 設計資料はあるが本件の正式閲覧画面への実装は未確認 |
| `future_candidate` | 追加候補 | 現時点で画面として未実装。データ取得・集計・仕様策定が必要な場合がある |

`reference_path` は「該当機能の調査開始点」であり、**そのファイルが存在するだけで機能を実装済みと証明するものではない**。`data_readiness=available` も「該当スキーマ・APIが存在する」であり、任意のゲーム保存データに全ての成績が埋まっている保証ではない。

**現状の初期仕分け（Stage42）**：簡易GUI 22、読取モデルのみ 10、隔離プレビュー 6、設計のみ 4、将来候補 29、合計 **71**。これは機能数であり、開発進捗率・品質達成率ではない。

## 3. 閲覧機能の全体構成（設計の軸）

### 3.1 ホーム・日付別試合（`VIEW-HOME-*`、`VIEW-DATE-*`）
年度を選択してシーズン概要を眺め、試合日・季節（春・夏・秋）・大会種別・都道府県で結果を絞り込む。「本日」を表示する際は**OSの現在日付とゲーム内シーズン進行日を分ける**。実際の試合日がわからない大会は「日付未定」。週・月カレンダーや注目カードは候補。

### 3.2 大会・地区予選（`VIEW-TOUR-*`）
春夏秋の全国・地方・地区大会を大会IDで選び、勝敗・ラウンド・トーナメント表・進出先を閲覧する。単純な勝ち抜きだけでなく、**地区予選・ブロック戦・敗者復活・代表決定戦・任意順位戦**を正しい意味で描き分けたい。現行の簡易ブラケットはMAIN優先で、複雑方式を正式再現したわけではない。2026広島秋西の状態プレビューは史実二次資料の段階再生で、全国共通の大会生成エンジンとしては扱わない。

### 3.3 試合詳細（`VIEW-MATCH-*`）
スコア・勝敗・日時・試合の出典に加え、将来的にはイニング別得点、チーム安打失策、打者／投手の試合別成績、打席イベント、継投、コールド・延長の理由を閲覧する。**イベント取得APIがあることと、試合詳細画面が完成していることは異なる。** イニング別スコアや全交代履歴などは現行の記録から確実に復元できると仮定しない。

### 3.4 学校（`VIEW-SCHOOL-*`）
正式学校マスター名・所在地・所属都道府県/地区、年度別勝敗、通算実績、現役選手、チーム能力の時間変化、公式の予選進出状況をまとめる。学校能力は固定的な「打撃力80」ではなく、**その時点の選手・起用・状態からの派生snapshot**を使う（`team_strength_design.md`）。観測試合名と正式学校IDは別のもの。広島西部18校はStage39で一意照合済みだが、全国の全予選について保証したわけではない。

### 3.5 選手・成績ランキング（`VIEW-PLAYER-*`、`VIEW-RANK-*`）
個人プロフィール、当該年度・大会ごとの打撃／投球成績、ロスター、年度を跨ぐキャリア、能力、表彰など。大会ごとの打撃・投手ランキングはStage13D3のGUI試作がある。率指標は記録済みの整数カウントから集計する。**年度を跨ぐ同一選手IDの継続性は先行文書の課題**であり、careerランキングの表示を無条件に実装済みとは判定しない。

### 3.6 記録・比較・検索・出力（`VIEW-HISTORY-*`、`VIEW-ANALYTICS-*`、`VIEW-NAV-*`、`VIEW-EXPORT-*`）
歴代優勝校・学校の年度推移・高校別勝率など「ずっと眺める」価値が高い情報を候補にする。学校・選手・大会・試合のリンクは**ID＋年度**で構成し、表示名や検索順位で結ばない。成績の比較、都道府県別の傾向、画面からのCSV出力などは候補であり、今回決定済みの実装順ではない。

### 3.7 出典・未確定表示・使いやすさ（`VIEW-META-*`、`VIEW-UX-*`）
試合日付と得点の由来（生成結果、入力上書き、公式確認、二次結果、日付未定）、予選の本戦出場決定と任意順位戦、結果確定と対戦校未定を明確に表示する。CSV・SQLiteが未収録のときは0点や0打率と偽装しない。Windowsの表示・DPI・キー操作はGUIなしのCIでは確認できないため、手動受入が残る。

## 4. 仮優先度（Stage43で再判断する）

| 優先度 | 意味 | 主な機能例 |
|---|---|---|
| **P0** | 閲覧中心ゲームの初期版成立に必要と考えるもの | シーズン概要・日付別試合・大会一覧/結果/組合せ・試合スコア・学校概要/戦績・ロスター/選手・大会ランキング・データ出典区別 |
| **P1** | 初期版後の使いやすさ・深掘り、またはP0を支える確認が必要 | 詳細試合経過、歴代大会実績、学校能力閲覧、年度別推移、検索の復元、複雑方式の可視化 |
| **P2** | 後から追加できる候補 | 高度比較、記録グラフ、任意CSV出力、お気に入り、デザイン表現 |

これは**優先度案であり合意済み要求ではない**。高い優先度でもデータが不足していれば、実装順は依存関係を優先する。各行のデータ準備状況は`viewing_data_requirements.md`で再評価する。

## 5. 最小のユーザー閲覧シナリオ

1. ホームで年度・シーズン概要を確認 → 日付別で本日の結果を開く → 大会・対戦校へ移る。
2. 春・夏・秋の大会一覧 → トーナメント表 → 試合 → 学校 → ロスター → 選手個人成績。
3. 大会結果 → 大会別打撃/投球ランキング → 個人プロフィール → 該当学校の戦績。
4. 学校検索 → 年度別戦績 → 試合履歴 → 大会結果 → 別年度の同一学校。
5. 複雑な地区予選では、途中状態・公式根拠・代表校決定と順位戦の区別を維持。試験用の二次結果は通常ゲームのシミュレーション戦績へ合算しない。

画面の配置案と遷移のガードは`viewing_screen_navigation.md`を参照。

## 6. 仕様変更に強くする運用

- **機能IDを固定**（例 `VIEW-SCHOOL-006`）。PR・設計資料・テストで同じIDを用いる。機能を分割する場合は新IDを採番し、旧IDの置換関係を記録する。
- 表示項目の追加要求が出たら、まず台帳へ機能ID・閲覧したい値・時点・必要データと保存先・欠損表示・優先度案を追記。read modelの依存関係を確認してからGUIへ進む。
- 見た目・画面配置を決める前に、試合・学校・選手・大会の**事実の所有者（source of truth）**とID・年度・出典を決める。
- 正式ゲームUIの画面レイアウト・色・素材はこのStage42では確定しない。Tkinterの試験UIを正式GUI仕様の完成形とみなさない。
- **テスト成功とWindows実機の表示確認は別項目**。Stage41までの実機10件は未実施のまま。
- Stage43でP0・P1・P2と不足データの優先順位を改めて承認する。Stage44で画面遷移と導線を精緻化し、Stage45以降に不足read modelを段階実装する。
