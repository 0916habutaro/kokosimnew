# Stage 43G-60：旧A方式／v2の保存年度を分離したまま発見・閲覧する契約

作成日：2026-10-11

## 背景

従来の `historical_matches.sqlite3` は年9999までのISO日付を前提とし、年10000以降の `fictional_option_a_v2.sqlite3` は `G10000:04-01` 等の論理日付で架空ゲーム用に別保存される。Stage43G-30〜37では封印済み年度の選択、学校／選手の年別閲覧、成績表、Tkinter試験画面を実装したが、試験画面の起動には `--years 2026,10000` のような年度明示が必要だった。

本Stageの目的は**実際に保存済みの旧方式・v2年度を、小さな候補ページから発見して既存の安全な閲覧導線へ渡すこと**。2形式のゲーム記録を同一SQLiteや単一時系列へ移行しない。

## 実装

1. `CareerCrossEraYearCatalog.page(limit=24, offset=0)`：封印済みの年度ヘッダのみを各SQLiteに読取専用で問い合わせ、年の降順にマージした**一覧**として返す。各ソースは最大 `offset + limit + 1` 行しか読まず、全試合JSONを展開しない。1ページ24年度以下で年10000以降を自然に含める。
2. ヘッダだけでは封印ledger、実試合のSHA、保存カレンダーSHAまで証明されないため、年度候補には `sealed_header_unverified` と明示する。
3. 年度と固定学校IDを明示的に指定する `select_school(year, school_id)` は既存 `CareerCrossEraNavigator.school_page([year], ..., verify_source=True)` に処理を委譲し、各原本の封印ledger・SHA・日付形式・学校年度ロスターの帰属を確認してから表示する。
4. 旧A方式が年9999を超える、v2が年9999以下を主張する、表示ページに二重年度が混じる場合は拒否する。さらに閲覧時の既存read gateが**全年度ヘッダ**に対する衝突を検証する。
5. クロス年度Tk試験画面の起動引数 `--years` に `saved` を追加。最新24年度が候補で、`--year-page-offset 24` 等を指定して古い候補ページを選択可能。従来の `--years 2026,10000` はそのまま利用できる。これにより年10000の実験記録を手入力なしでも一覧から選べる。

### 利用例（保存済み実験スロットのみ）

```bash
python -m phase2_engine.career_cross_era_gui_pilot --slot out/saves/EXAMPLE --school-id SCH000001 --years saved
python -m phase2_engine.career_cross_era_gui_pilot --slot out/saves/EXAMPLE --school-id SCH000001 --years saved --year-page-offset 24
```

## テスト境界

- 2026年旧A方式・10000年v2とも**合成された別々の封印済みテストデータ**から年度一覧を取得し、日付形式・学校別試合・試合詳細の年度分離と元SQLiteのハッシュ不変を確認する。
- v2試合SHAを壊した場合、候補一覧には未検証のヘッダが残りうるが、学校／試合は表示できないことを確認する。
- 未保存年、誤った限度、形式混在、存在しないSQLiteは勝手に生成しない。
- 既存Stage43G-30〜32のE2E回帰、Python全unittest、関東E2Eの成功後のみmainに反映する。

## 明示的に未実装

- 2026→10000年を連続シミュレーションしたわけではない。別々のセーブ実験であり、介在する年度の学校や所属選手は検証されていない。
- 旧A方式とv2のスコアや通算成績を自動合算しない。日時の単一時系列ソートも行わない。
- 2027年以降の現実の高校野球の出場校、試合、優勝校を推定しない。
- 年10000以降の全国大会・年度更新エンジン、および正式ゲームGUIは引き続き未実装。

次工程では、登録年度ヘッダを検証済みの要約インデックスへ段階的に最適化し、年代切替・表示名・将来のゲーム進行エンジンと正式画面を独立した契約として整理する。
