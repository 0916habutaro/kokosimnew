# Stage 43G-13：3,000校以上×50／100年の歴史SQLiteスケール監査

作成：2026-10-10。対象：高校野球ゲーム「ココシミュNew」Stage43G-12後の長期成績保存設計。

本Stageは年数無制限プレイの性能課題を明確にするための**索引改善と再現可能な負荷測定**であり、全国全大会の自動進行や3,000校×100年の実ゲーム完走を証明するものではない。

## 1. 前提と永続化範囲

- 保存する試合履歴はA方式。試合スコア、イニング別得点、チーム／打者／投手個人成績を保存し、打席ごとのイベントは永続化しない
- 年度別ロスターは1校20名。固定選手IDを保ち、1年生→2年生→3年生、卒業と新入生を反映。新入生は現行の学年構成により8→7→5→8…の3年周期となる
- 学校×年度×大会の戦績、歴代在籍選手、個人IDの年度別推移をSQLiteで検索。3,000校×100年分を一括してJSON展開しない
- これまでの学校ID・選手ID・学校名は改変しない。試合のSHA256や選手IDの改変検査を維持する

## 2. Stage43G-13実装

### 学校先頭の長期間検索索引

従来の idx_history_team1 / idx_history_team2 は年度が先頭の複合索引で、特定校の50～100年横断検索では広い年度範囲を走査し得るため、以下を追加した。

- idx_history_school1_year = (team1_id, year, competition_id, match_id)
- idx_history_school2_year = (team2_id, year, competition_id, match_id)

年度先頭の従来索引は年度別一覧向けとして維持する。CREATE INDEX IF NOT EXISTSにより既存SQLiteにも追加できるが、大きな既存DBでの初回索引構築時間と空き容量は別途監査が必要。

### 学校歴代戦績のストリーミング取得

phase2_engine/career_longitudinal_read.py の school_results を、学校IDと指定年度範囲の試合レコードをSQLiteカーソルから順に取得し、年度×大会別に集計する実装へ変更。

全試合をfetchallしない。返却用のページ（最大200グループ）のみ保持する一方、**ページ外も保存済み試合SHA・スコア・勝者の整合性チェックを省略しない**。試合から大会優勝／順位を推測しない。

### 実スキーマを使用する合成データ負荷試験

phase2_engine/career_history_scale_audit.py は既存の HistoricalMatchArchive.sync と CareerRosterArchive.save_initial_roster / advance_and_save を使って書き込み・封印・年次保存・読み取りを行う。

- 学校IDは登録マスターから取得。ただし対戦カード、得点、打者・投手成績はすべて合成試験データ。実在の大会結果ではない
- 9イニング得点、18人の合成打者、2人の合成投手のA方式型JSONを使う。実際の試合エンジンで能力計算した結果ではない
- 1年ずつ年次台帳を封印し、実際の20人ロスターから進級・卒業・新入生を保存
- 実測するもの：両SQLiteファイルの物理容量、書き込み所要秒数、学校歴代戦績・歴代選手ページ・個人在籍年の検索時間（中央値・p95・最大）、EXPLAIN QUERY PLANでの索引使用
- 大規模データ作成には --allow-large の明示が必要。既存SQLiteの上書きを禁止する

## 3. 規模の算式（速度・容量の実測値ではない）

ベンチマーク設定：1校につき1年4試合。対戦校同士を二重カウントしない。

| 指標 | 3,000校×50年 | 3,000校×100年 |
|---|---:|---:|
| 学校年度ロスタースナップショット | 150,000件 | 300,000件 |
| 延べ年度所属選手人数 | 3,000,000人年 | 6,000,000人年 |
| 累積選手ID数（初年20人＋8/7/5周期） | 1,044,000人 | 2,040,000人 |
| 合成試合数（4試合／校／年、2校で1試合） | 300,000試合 | 600,000試合 |

上記は計算上の件数にすぎない。実際の大会試合数、成績JSONの大きさ、SQLiteページ・索引・空き領域、バックアップ世代により必要容量は変わる。小規模のバイト単価から算出した見積もりを大規模実測と呼ばない。

## 4. 再現手順

小規模測定：

    python -m phase2_engine.career_history_scale_audit --schools 16 --years 3 --report out/stage43g13_small.json

50年実測（開発環境のディスク空きを確認して新しい空ディレクトリを指定）：

    python -m phase2_engine.career_history_scale_audit --schools 3000 --years 50 --allow-large --output-root out/audit_3000_50 --report out/audit_3000_50.json

100年実測：

    python -m phase2_engine.career_history_scale_audit --schools 3000 --years 100 --allow-large --output-root out/audit_3000_100 --report out/audit_3000_100.json

テスト単独実行：

    python -m unittest discover -s tests -p "test_stage43g13_history_scale.py" -v

実行レポートJSONには対象学校数・年数・合成試合数・各DB容量・測定時間・クエリ計画を記録し、合成データであることを必ず明示する。スケール変更した場合は別測定として扱う。

## 5. 回帰監査

tests/test_stage43g13_history_scale.py に次の4試験を追加。

1. 16校×3年・96試合（合成A方式個人成績）と48校年度ロスターを実スキーマに保存し、実測容量と索引／検索レイテンシを検証
2. **4校×100年（2026～2125年）**、800合成試合、400学校年度ロスターを書き込み、各年を封印。学校成績200グループ、学校歴代680人（初年20名＋99年間の新入生660名）の深いページを検査。容量・検索レイテンシをCIログに出力
3. ページ外に位置する最後の年の試合を改変した場合でも、先頭の学校戦績ページを取得する処理が改変を検出
4. 3,000校×100年の無許可生成、奇数学校など不正値、既存SQLite上書きを拒否

**このCIの「100年」は4校の合成データを実際に保存・検証した意味であり、全国3,000校×100年の速度やゲーム進行を証明しない。**
