# Stage 43G-1：2026年の封印履歴を保持した2027試験大会の開始・保存・再開

作成日：2026-10-10
前提：Stage43F-7（PR #141、main反映済）
区分：**限定的な年度間ゲーム統合の第一段階**。全国162大会の年度一括生成や本編`LiveGameService`年度切替の完成ではない。

## 1. 現行の問題と対応方針

2026年の本編`LiveGameService`は`LiveSeasonGraphPlanner`で、該当年度の大会・日程・進出関係を計画し、それを`LiveSeasonSave`で再現可能に保存する。現在の正式大会マスターは2026年度中心であり、2027年度の学校・地区分け・大会組合せ・選抜選考・2026東京秋季大会の登録などには未解決事項がある。この状態で`LiveGameService.new_game(year=2027)`を解禁すると、存在しない大会や学校所属を公式データとして確定させることになる。

Stage43G-1では**既存の2026本編セーブ形式・復元契約をいっさい変更せず**、同じセーブ枠へ将来年度の「**1大会だけのゲーム内sandboxチェックポイント**」を追加する。

新ファイル：`phase2_engine/career_preview_checkpoint.py`

### 主なAPI

| API | 内容 |
|---|---|
| `CareerPreviewCheckpointService.start(...)` | 2026終了・封印済みの試合履歴＋前年秋の確定順位＋2027進級済みロスター＋明示した大会出場校・地区所属から2027大会を作成し、初期チェックポイントを保存 |
| `play_next_date(session)` | 次のゲーム内仮日程を1日進め、完了試合をJSONとA方式SQLite履歴へ保存 |
| `load(slot_id,year,competition_id)` | 元の入力と前年履歴を再検証して新規エンジンを構築し、保存済みの日付を決定論的にリプレイして、中断時と同じ状態を復元 |
| `session.summary()` | 前年封印・ゲーム内2027仮日程・再開可否・試合数を表示。全国本編が開始可能になったとは報告しない |

## 2. 正本とファイル配置

同じゲームスロットで次のデータを使う。

```text
<save_root>/<slot_id>/
  manual.json / autosave.json       # 従来の2026本編セーブ（変更しない）
  historical_matches.sqlite3       # Stage43C/D：2026 sealed、2027 active
  career_rosters.sqlite3           # Stage43E：2026/2027選手の恒久ID
  career_previews/
     2027_CMP000084.json           # Stage43G-1：試験用1大会チェックポイント
```

`HistoricalMatchArchive.register_next_year()`が2026のsealedを確認し、2027を隣接年として登録する。2027は**active**で、試験用大会の完了試合が同じA履歴DBへ追記される。2026年の試合・順位・封印レコードを消去または置換しない。

**1つのスロットにつき、1年度・1試験大会だけ**に制限。年度の全競技の試合や将来大会の資格を、本編から完全に進めることはまだできない。既存の`CareerCompetitionOutcomes`が2026前年秋の全MAIN試合を保存済み試合と照合した結果だけを使う。

## 3. 決定論的な中断・再開

新しいチェックポイントは以下を記録する。

- 明示されたゲーム内年・大会ID・全参加校ID・地区別所属・`base_seed`・`career_seed`・前年秋の明示ゲーム大会ID（東京のみ）
- 2026年次封印試合台帳SHA-256
- resolver契約とこれらの入力から作った不変plan fingerprint
- 完了したゲーム内試合日一覧・試合件数・全完了試合のA方式出力SHA-256
- JSON本文のSHA-256チェックサム、ゲーム内仮日程・本編未完成の明示フラグ

保存処理では一時ファイルを使って`os.replace`による原子的なJSON置換を実行し、その後にSQLiteへ追記する。SQLite書き込み前にプロセスが終了しても、次回読み込み時に元の入力・seed・進級済みplayer_idから同じ試合を再現し、試合履歴を不足分だけ追記する。

読み込み時は当該日付を**1日ずつ再実行**する。期待する日付・試合数・全試合fingerprintが合致しなければロードを拒否。確定済みの2026年歴代試合の改変や、2027途中状態を別のseedで上書きすることも拒否する。

複数の古いセッションが同じチェックポイントを上書きしないように、保存時には前回読み込んだチェックサムを確認する。保存ファイルを改ざんしてチェックサムを再計算した場合でも、試合結果の決定論的な照合により不一致を検出する。

## 4. 実装上の意図的な制限

- `CareerPreviewCheckpointService`は本編`LiveGameService`の2026→2027完全移行機能ではない。既存の`LiveGameService`と`LiveSeasonSave`のセーブ互換性を守るため、チェックポイントは別ファイルとして管理する。
- 出場校・地区所属はStage43F-5～7の**ゲーム用明示sandbox入力**。将来年度の実世界の公式出場校・日程を確定したことにはならない。
- 進級・卒業・新入生処理は既存`CareerRosterArchive`で**あらかじめ対象校の2027ロスターが保存済み**であることが必要。欠損校を別seedで再生成しない。
- 現在は`future_prior_autumn_access_bridge`が対応する前年秋の予選免除大会のみに接続。センバツ委員会選考・広島2026の未確認ルート・東京秋公式マスター未登録部分は仮定で自動補完しない。
- 完了した2027の大会順位を正式な翌2028への自動出場資格としてシーズン横断登録する機能は未実装。
- ファイル・SQLiteにまたがる単一トランザクションではない。JSONを先に原子的に保存し、SQLiteの取りこぼしは**検証済みの復元リプレイにより修復**する。JSONが破損している場合は勝手な結果の補完をしない。
- シード権の根拠が別途必要な場合は、前年成績からの推測順位を入力しない。

## 5. 受入テスト

`tests/test_stage43g1_career_preview_checkpoint.py`の10テスト：

1. 2026年度の3試合と大会順位を保存・封印し、39校の2026→2027進級済みロスターを作成。
2. 同一ゲームスロットで2027茨城春季大会の試験プレビューを開始。既存手動セーブと2026歴史を維持し、履歴DBに2027activeを登録。
3. 最初の2027-04-08試合日を実行、4試合のA方式イニング別得点・打者・投手記録を2027履歴へ追記。
4. 途中状態を新たなサービスインスタンスから読み込み、同じ試合・次の日付を再現して進行。
5. JSON保存後・SQLite保存前のクラッシュを模擬し、SQLiteの欠損試合がリプレイで補われる。
6. 不正チェックサム・チェックサムを再計算したスコア改変・2026封印台帳改変を検出して拒否。
7. 古い2つのセッションの競合保存・二重起動・1年度に異なる複数大会を同時登録しない。
8. 不正なスロットID・前年未封印の開始を拒否。

## 6. 次のStage43G-2以降

- 完了した2027試験大会の`CompetitionRun`を当該年度の履歴として確定するには、**全国の同年度大会が完了・年次封印した時点で**`CareerCompetitionOutcomes`へ追記する必要がある。単独試験大会の終了と2027年度の全大会終了を混同しない。
- 単独大会用の年次アーカイブidentityを全国複数大会のplan identityへ移行する設計と、その永続性・互換性を監査する。
- 2027年の年度マスター、学校の年次加盟・所属、予選方式、試合日、全国地区・甲子園、センバツ選考の未解決を明示的に扱う`LiveSeasonGraphPlanner`の年次入力インターフェースを作る。
- 2026本編セーブから安全に**2027年の年間プランを確定し、年度全体のプレイ・セーブ・ロードを切り替える**本当のゲーム年次移行を実装する。
- ゲーム閲覧用read model（年度別学校成績、選手・大会・試合別A方式記録、歴代大会結果）を複数年で連続閲覧できる形へ接続する。

Stage43G-1で達成するのは**「2026の確定履歴を保持したまま、2027年の試験用1大会を保存・中断・再開して実際に試合を継続する」**という一体動作。
