# Stage 43D：年度境界・長期キャリア履歴の基礎契約

作成日：2026-10-10
依存：Stage 43C / PR #132（マージ後CI成功）
対象：履歴SQLiteと年度終了の検証。**2027年度以降のゲーム実行は未実装**。

## 1. 目的と今回の到達範囲

ユーザー要件は、年数に人為的な上限を設けず、歴代大会・試合・学校戦績・所属選手を後から閲覧できること。

Stage43Cではセーブ枠の `archive_identity` に **初年度・seed・計画fingerprint** が固定されており、翌年度が正しく生成されても、別年度のデータを同じ履歴DBへ登録できない。この制約を、過去記録の不変性を失わずに解消するために次を実装する。

- `career_years`：セーブ枠内に年度・seed・resolver契約・年度計画fingerprintと、`active/sealed`の確定状態を管理。
- `HistoricalMatchArchive.seal_year()`：終了年度の確定試合件数を照合し、その時点の行鍵／SHA-256一覧の台帳digestを記録。再実行は冪等。
- `HistoricalMatchArchive.register_next_year()`：**直前年度がsealedで、年差が正確に1**の場合のみ次年度の別seed／計画を登録。同じ年・同じfingerprintの再実行は冪等。年飛ばし／異なる計画は拒否。
- `HistoricalMatchArchive.sync()`：既存初年度のアーカイブIDを維持し、登録済みの別年度に限り試合を追記可能。既にsealedの年度に新しい試合は追加不可、同一試合の再保存は許容、改変は拒否。
- `year_transition.year_end_readiness()`：現年度の12月31日・依存大会全件completed・未実施試合／日程ギャップ0などを確認。満たさない場合は封印を禁止。
- `LiveGameService.finalize_season()`：判定をパスした年度のみ、JSON手動セーブ→履歴SQLite同期→件数照合・年度封印を行う。**このメソッドでは2027年のゲームを起動しない**。
- Stage43Cアーカイブには次回同期時に`career_years`を追加する非破壊のスキーマ拡張。既存`historical_matches`や`archive_identity`の行は保持する。

## 2. 年度間の状態遷移

```text
2026 active
  ├─未解決の大会・日程不足・試合待ち → 年度封印不可
  └─12月31日・全大会確定・履歴件数照合
       ↓ finalize_season
2026 sealed（不変の記録）
       ↓ register_next_year（履歴DBの年度枠だけ登録）
2027 active（*大会・選手生成は後続工程*）
       ↓ ... 成立すれば
2027 sealed → 2028 active → ...
```

年数上限を履歴DBのビジネスロジックに埋め込まない。100／500／1000年は試験点とする。SQLite整数・ディスク容量など物理的な制約は別途あるため無限容量を保証する意味ではない。

## 3. 互換性・保護

| ケース | 扱い |
|---|---|
| 同じ年度の同じ試合を再保存 | 内容一致ならスキップ |
| 同じ年度の同じ試合を別結果で保存 | エラー（旧記録を保持） |
| 年度封印後に新試合を追加 | エラー |
| 年度封印後に元のセーブをロード | 既存試合の冪等同期のみ許す |
| 旧年度と新年度で大会ID・試合IDが重複 | 年度が複合キーに含まれるため別試合として保存 |
| 前年が未封印のまま来年を登録 | 拒否 |
| 2026→2028の飛び越し | 拒否 |
| 2027年登録時に同じ年度へ別seed／計画を混ぜる | 拒否 |
| 2026資料をそのまま2027公式日程として流用 | **本実装は行わない** |
| Stage43Cの既存履歴ファイル | 最初の再同期で年度管理テーブルを追加。既存試合行は変更しない |

**アーカイブ封印は年間試合台帳の不変境界であり、連続年度の大会・選手がすでにゲーム内で動くことを意味しない。**

## 4. 翌年度ゲームを実際に進めるための追加要件

### 4.1 大会と日付

`LiveSeasonGraphPlanner._competition_rows()`は`reference_year`で2026を絞り込む。2027年の大会／トーナメント／組合せ・出場校・ルール・日程を作る計画生成器が必要。

- 2026年度の実在の公式日程と、2027年以降のゲーム生成日程を区別する。
- 前年秋→翌年春選抜の選考・参加枠を年度跨ぎで引き継ぐ。
- 日付・出場枠が未確定の場合は`calendar_gap`として公開し、架空の公式情報を断定しない。
- Pythonの`datetime.date`は9999年が上限。年数無制限方針では、長期的には独自の暦／通算日数表現が必要。

### 4.2 選手ID・進級・卒業・新入生

現行`PlayerRosterGenerator`は選手IDに **reference_year と roster_no** を含める。このまま2027年に再生成すると同一選手のIDが継続しない。

- **在学選手のplayer_idは不変**。学年だけ1→2→3と進める。
- 3年生の卒業・新1年生の入学は、既存IDの継承と新規ID生成を分ける。
- 氏名一致で同一人物と判定しない。学校ID＋入学年度＋個体識別子、もしくは既存IDの永続保存が必要。
- 現行の学年人数は1年5人、2年7人、3年8人で均等でないため、既存20人を単純に一学年進級させるだけでは翌年度も20人を維持できない。**人数配分・増減員・ベンチ入り／所属全体の概念を別途決める**。
- 同じ選手の打撃・投手成績、所属歴、年度別能力変動、卒業年度を同じIDへひもづける。
- 学校の休部・統廃合・合同チームを想定し、学校マスターと大会出場チームIDを混同しない。

### 4.3 セーブ・ロード・GUI

現在のライブJSONセーブは`plan_fingerprint`・単一年・seedに結びつく。年度を跨ぐセーブ形式の拡張では、**キャリアマスター（セーブ枠）＋年度単位セーブチェックポイント**を分ける必要がある。古い年度は不変、ロード時は該当年の計画・選手状態に基づき復元し、履歴DBと照合する。正式GUIでは年度切替を実装し、過去年度を表示しただけでゲーム進行が巻き戻らないようにする。

## 5. 検証

`tests/test_stage43d_career_year_boundary.py`で確認：
- 2026 sealed→2027 activeで同名match_idを別年度に保持。
- sealed済み年度の新試合・改変を拒否し、同じ内容の再同期は可能。
- 飛び越し・未封印の翌年度登録・計画fingerprintとseedの取り違えを拒否。
- 完了済みセーブだけを年度封印し、未解決の大会・日付ギャップ・年末前は拒否。
- Stage43C旧SQLiteからの非破壊移行。
- 旧記録の保存と同時に、次年度のゲーム進行は開始したと偽らない。
