# Stage 43G-23：無制限年数に向けた年度別増分保存監査・索引利用確認

作成日：2026-10-11。前提：Stage43G-22 PR #163（main反映済み）。

## 目的
現在の履歴保存はA方式（試合結果、イニング別得点、選手個人成績）を永久保存し、派生個人成績キャッシュは破棄・再作成可能という設計。Stage43G-22は2校×20/50年の総容量を測定した。Stage43G-23では「**1年増える際に何が何バイト追加されたか**」を追跡し、長期セーブの肥大化要因と主要SQL索引の採用を監査する。原本JSONやSQLiteスキーマの圧縮・変更・マイグレーションは行わない。

## 追加
`phase2_engine/career_annual_growth_audit.py`：

- `profile_annual_growth(matches, rosters, cache)`：既存3DBに`mode=ro`＋`query_only=ON`で接続し、保存された各年度の原本試合、学校20人ロスタースナップショット、新入部員などの恒久選手ID、派生個人成績の**UTF-8文字列バイト数とレコード数**を集計。各JSONをSHA-256で照合。元年度の封印台帳と派生学校年度キャッシュの元台帳SHA・件数の一致も確認する。
- 2026開始時の2・3年生は入学年が2024/2025等であっても、2024/2025のゲーム用大会・セーブ年度は作らない。最初に実際に保存した2026年度へ初期部員の恒久ID保存コストを帰属し、`bootstrap_prior_entry_year_identities`として報告する。
- `career_years.status='active'`の年度も閲覧可能。封印済み年度とは区別し、active年度にsealed由来キャッシュを偽装して存在させていた場合は拒否する。欠損した連続年度、封印された年の試合件数変化は拒否する。
- `physical_year_snapshot`：合成ロスター→A方式試合登録→年封印→派生キャッシュ作成後の**実際の3DBファイルバイト数**を毎年取得。前年度との差分を追加。SQLiteのページ再利用により差分が0やマイナスになる可能性を許容し、年別論理payloadサイズから物理ファイル増分を推定したものとは混同しない。
- `school_query_plan_audit`：主要4クエリについてSQLiteの`EXPLAIN QUERY PLAN`を読み取り専用で取得し、学校home試合・away試合、歴代部員ID一覧、選手キャッシュの索引が**単なる存在ではなく実際に使われたか**確認。
- CLI：`python -m phase2_engine.career_annual_growth_audit --matches ... --rosters ... --cache ...`。学校／選手ID／開始・終了年度をすべて渡せば索引利用の詳細を併記。既存3DBを書き換えず、必要に応じ明示指定した`--output-json`先へ報告だけを書き出す。

## 長期合成ベンチマークへの接続
`run_full_a_benchmark`は従来のA方式試合・本物の保存済みロスター選手ID・封印年度キャッシュの整合性テストに加え、**毎年の物理容量スナップショットと最終時点の論理payload年度別内訳、クエリプラン**を出力。20年・50年専用CIを既存`.github/workflows/option-a-storage-profile.yml`で継続し、実測JSON artifactとして30日間保持する。

## 計測の意味と不変条件
- **論理payloadの年度別UTF-8バイト数**：各表に保存されるJSON文字列のサイズ。SQLiteのB-tree、索引、行メタデータ、未利用ページは含まない。
- **物理SQLite容量スナップショット**：年末に3DBファイルが割り当てられたページ全体のサイズ。個別レコードの追加コストそのものではなく、索引とSQLite内部領域も含む。
- 学校の歴代成績表示に使うA方式原本は削除・移動・変更しない。キャッシュは再生成可能な派生であり、原本と混同しない。
- 原本のレコードSHA、ロスター・恒久選手ID・キャッシュ選手年度SHAをチェックするが、**全試合の封印台帳SHA再計算やキャッシュ学校年度fact全件再計算を意味するものではない**（元の実装の厳格検証が別途存在）。
- パフォーマンスと索引利用は現在の模擬2校×20/50年に限る。全国3,000校×100年の結果、正式GUIの実機速度、実大会の年間試合数には外挿しない。

## テストと受け入れ
`tests/test_stage43g23_annual_growth_audit.py`：年度別論理バイトの総和一致、3DB物理増分の累積一致、初期高学年の入学年問題、封印・activeの区別、改ざん拒否、4種索引選択、DBの読み取り不変、欠損ファイル新規生成禁止、年度スナップショットの順序検証。

通常Python 3.12全テスト、関東8都県17校E2E、フルA専用ベンチマーク、20/50年専用監査の**4ジョブ**すべて成功してからmainマージする。

## 未実装・今後
実際の全国高校野球3,000校×50/100年の全工程実行、長期間の実大会日程・選手卒業と入学・能力変化の完全年次ゲームサイクルは未検証。「年数無制限」を実現するには、9999年を超えるとISO日付が表現できない問題、ゲーム年番号と公式大会に使う暦年の分離、外部CSV大会カレンダーの反復規則、物理DB容量の増加に伴うアーカイブ分割／バックアップ運用を別途設計する必要がある。Stage43G-24ではこれらの**長期ゲーム年番号・カレンダー設計の契約化**や、ゲーム年度をまたぐ増分バックアップの検証を候補とする。
