# Stage 43G-2：同じ年度・同じセーブ枠で複数の翌年度大会を保存・再開する

作成日：2026-10-10  
前提：Stage43G-1 PR #142 のmain反映・マージ後全件CI成功  
完成範囲：ゲーム内2027年の**複数独立試験大会**について、前年2026の封印試合・順位・永続選手IDを参照し、年度共通identityで2027試合を保存／ロードする。

## 1. 背景・なぜ別のセーブ名前空間を作るか

Stage43G-1は`career_previews/2027_CMP000084.json`のように**1つのスロット／年度につき1大会**に制限した。そこで使う年次identityは当該大会の出場校・seed・前年封印台帳に由来するため、別大会のidentityと混ぜると`HistoricalMatchArchive.register_next_year()`が拒否する。

Stage43G-2では**開始する複数大会全体の入力と初期組み合わせを一括fingerprint化**し、`HistoricalMatchArchive`へ一度だけ2027年identityを登録する。両大会の試合は同じ`historical_matches.sqlite3`の`year=2027`に追記する。2026年のsealed履歴・大会順位と、既存`manual.json`/`autosave.json`は不変。

```text
<save_root>/<slot_id>/
  manual.json / autosave.json        ← 2026年本編セーブを触らない
  historical_matches.sqlite3        ← 2026 sealed / 2027 active
  career_rosters.sqlite3            ← 2026→2027進級済みplayer_id
  career_multi_previews/
    2027.json                        ← 複数大会共通チェックポイント
```

既存Stage43G-1の`career_previews/2027_*.json`とStage43G-2は、**同一スロット・同一年度では相互排他的**。Stage43G-1の既存ファイルがある場合は開始を拒否し、同時に既存SQLiteの2027identityが別のものなら`register_next_year`で拒否する。移行・マイグレーションを勝手に行わない。

## 2. 新しいAPIとデータ契約

新モジュール：`phase2_engine/career_multi_preview_checkpoint.py`

- `CareerMultiPreviewCheckpointService.start(slot_id,year,competitions,base_seed,career_seed)`：2つ以上の`competition_id`と、その大会の全参加校・全地区の明示的な割当を受け取る。前年sealed台帳・確定秋県大会結果・全校の当年ロスターを検証したうえで、**年度共通**の入力identity・初期試合組み合わせdigestと初期JSONを作成。
- `play_next_date(session)`：全大会の未処理試合日で最も早いゲーム内仮日を選択し、その日に試合があるすべての大会を日付順に進行。同じ日付が両大会にあれば両方進める。試合の出典は`game_projection_v1`のまま。
- `save(session)`：これまで処理した共通日付一覧・大会別処理日・完了試合全文のfingerprint・完了大会の優勝校をチェックサム付きJSONへ**原子的置換**し、後から同一年度のA方式SQLiteへ一括追記。
- `load(slot_id,year)`：全大会の元の明示学校ID・地区割当・seed・前年台帳・初期組み合わせを検証して再構築し、共通日付を順番にリプレイ。全試合fingerprint・大会別処理日・完了大会優勝校の照合後、必要があればJSON先行コミットによるSQLite欠損を冪等補修。
- `session.completed_runs()`：**実際に完了した**大会の`CompetitionRun`を、予選からの勝ち上がり・大会順位を含むread-only情報として取得。まだこれらを同一年の別大会や翌年の正式出場資格へ**自動付与しない**。
- `session.summary()`：登録大会数、完了大会ID、処理済み日、同一年の試合数を表示。全年度のゲームが完成したと誤表記しない。

## 3. 最初の複数大会統合対象

2026秋のゲーム内の確定済み試合を保存・封印し、2027の試験用茨城春・埼玉春を同じセーブで進める。

| 翌春大会 | 出場校入力 | 前年秋直接MAIN | 地区予選参加 | 地区代表 |
|---|---:|---:|---:|---:|
| 茨城 `CMP000084` | 39校 | 4校 | 35校 | 31校 |
| 埼玉 `CMP000090` | 52校 | 8校 | 44校 | 40校 |

両県とも、元の`competition_access_rules.csv`にある`source_year_offset=-1`かつ`top_n`の地区予選免除枠を使う。2026秋の実史実記録を利用したわけではなく、**テストの中で完了させたゲーム内2026秋大会の結果**のみを根拠とする。2027年の地区所属や参加校を本来の公式情報と確定したわけでもない。

`career_rosters.sqlite3`の対象91校はそれぞれStage43Eの`CareerRosterArchive`で2026から2027へ継続生成され、同一player_idを維持する。2027ロスターがない学校については大会開始を拒否し、別人を新規ランダム生成しない。

## 4. 保護と回帰テスト

`tests/test_stage43g2_multi_competition_checkpoint.py`の10件で次の点を検証。

- 2026の封印済み秋県大会（茨城・埼玉）の結果を含む前年台帳を保持し、2027active年度に複数大会を登録。
- 同一セーブ枠で茨城4/8→埼玉4/10などの**試合日を横断する**進行とA方式の年次共通SQLiteへの保存。
- 中断後に2大会の組み合わせ・進行・記録をリプレイして復元し、次の日程に進める。
- JSONを先に保存した後のSQLite書込欠損をリプレイで修復し、2026封印試合に触れない。
- 保存済みJSONの改変・seedのすり替え、過去セッションからの競合上書き、2大会の重複指定、既存1大会プレビューとの同時起動、未封印前年の利用を拒否。
- 完了大会の`CompetitionRun`を返すAPIがあること、しかし未確認の大会間進出を勝手に自動化しないことを検証。

## 5. 設計上の残課題

1. **同一年の大会間進出**：春県大会上位校→春地区大会などを、年次・予選の順位・試合日と学校IDで照合し、後続大会の参加校へ渡す専用ゲートが必要。今回の`completed_runs()`は渡すべき正本の入口にとどまる。
2. **年度全体の保存形式**：今はsandbox複数大会のリストを開始時に固定し、途中の大会追加・県ごとの新規学校・合同チーム・センバツ等は扱わない。全国162大会の年次プランへの移行で初期plan fingerprint・同年度append-only制約を再設計する。
3. **全大会終了と年次封印**：2大会の終了≠2027年度の終了。今回2027を`sealed`へ移行するボタンは設けない。実際に年末までの全対象大会が完了してから封印する。
4. **他年度の学年進級**：現在の2027テスト入力は保存済みロスターが必要。翌2028への連続更新・登録は別工程。
5. **大会間シード**：上位成績＝次の大会の第1シードとしない。公式方式とゲームの契約が別途確認されるまで順位の自動優遇は行わない。
6. **公式資料の欠落**：東京秋の2026マスター未登録や広島地区の未確認経路は、推測で補完しない。

**Stage43G-2の成果は「同一2027年に複数の試験大会を開始→日付順に試合実行→A方式履歴を年次保存→再開すること」。本編の2026→2027年度全体移行ではない。**
