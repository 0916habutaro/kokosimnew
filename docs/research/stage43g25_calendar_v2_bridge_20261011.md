# Stage 43G-25：ゲーム内年度カレンダーv2と複数年度A方式セーブの接続試験

作成日：2026-10-11。Stage43G-24 PR #165は通常単体テスト／関東17校E2E／9999-10000年境界テスト成功後、mainへマージ済み。

## 目的

ユーザーが望む「実質的に年数の上限なくゲームを進め、いつでも学校・大会・選手の過去記録を見られる」を安全に実現するため、保存済みゲーム年度（正のSQLite整数）と、ISO日付`YYYY-MM-DD`とは**別のv2論理日付**を設計する。

**本工程はあくまで明示的に許可した合成・架空ゲームの日程のモデルと、2～5年度の保存・照合テスト。** 実際の2027年以降の大会日程や全国大会・地区予選の構造を2026公式資料から勝手に確定・反復するものではない。現行の大会runtime・既存試合原本・2026マスターの置き換えも行わない。

## 実装

### 日付表現 `GameDaySlot`

`phase2_engine/career_calendar_v2.py`で、`GameDaySlot(game_year, month, day)`を定義。

- `G2026:04-01`、`G2125:04-01`、`G10000:04-01`のトークン。Python`datetime.date`が対応しない10000年以降でも、年度・月・日の順序を比較できる。
- `day_of_year`は閏年を考慮。10000年は400で割り切れるためv2規則上は閏年と判定し、`G10000:02-29`を表現できる。一方、Stage43G-24の**従来の未承認カレンダー事前変換**では10000年の閏日を拒否する（矛盾ではなく、v2で明示的に採用したGregorian閏年規則の違い）。
- `iso_date`は1～9999の暦年だけで利用可能。10000以降は`None`。**トークンを従来の`historical_matches.match_date`に無断転記してはいけない**。現行2026/2027試合データの日付と混在しない。

### 架空ゲーム日程の明示登録・封印

`explicit_sandbox_plan(game_year, competition_days, approved_for_fictional_game=True, allowed_competitions=...)`

- `competition_days`は大会ID→「MM-DD」の明示的なリスト。入力大会IDがマスターに存在するかは`allowed_competitions`を渡して検証可能。重複日、対象年の閏日不整合、空・不正大会を拒否。
- `POLICY=opt_in_synthetic_calendar_v1`と`approved_for_fictional_game=True`が必須。**2026年度の公式日程の未承認再利用は禁止**。`source_kind=explicit_fictional_game_calendar_not_official`、`official_dates_proven=false`を記録する。
- 大会枠・シード免除・予選ブロック・地区代表決定はこの日付モデルからは導出しない。試合日の集合を記録する契約であり、本番2027年の大会生成ではない。
- `CareerCalendarV2Archive`は独立`sandbox_calendar_v2.sqlite3`に、年度別JSON＋SHAを保存。同一内容なら冪等登録、異なる内容なら衝突拒否。読み取りはSQLite `mode=ro`、原本セーブDBを新規作成・改変しない。
- 保存済みJSONに不正なpolicyやsource kind、日付、SHA変更があればfail-closed。記録された年度を上書きして勝手に修正しない。

### A方式試合・選手継続との接続

`run_full_a_benchmark(..., include_sandbox_calendar=True)`は既存の合成A方式基盤をそのまま使用し、任意で各年度の架空日程を明示登録。前年度の`seal_year`後にStage43G-24 `next_year_preflight`を通し、次年度ロスターの卒業・新入部員更新とゲーム試合記録・派生個人成績キャッシュを生成。

- `verify_sandbox_match_dates`で、保存済みの合成試合が当該年度・大会の明示日程内にあることを読み取り専用で全件照合。日付不一致・未登録大会・日付の形式異常はエラーで終了する。
- 過去年度のSQLite原本、ロスター、キャッシュ、新v2日程DBのSHAを閲覧前後で比較。既存のA方式スコア／イニング別／打者・投手個人成績、選手ID同一性、歴代成績の原本とキャッシュ一致、年度増分容量の検証を維持。
- **10000年度以降はv2日付の計画を保存できるが、まだ従来のA方式試合日付に変換できないため、現行の試合実行を許可しない。** `verify_sandbox_match_dates`も従来のISO試合日付のみ認める。

## テストとCI

`tests/test_stage43g25_calendar_v2.py`：
- 2026、2125、9999、10000の論理日トークンと年度/日順、閏日、不正な日時・非canonical入力、SQLite年上限。
- 架空ポリシーの明示承認、大会IDの許可集合、重複日拒否。
- v2年間カレンダーのSQLite保存・冪等性・改変検出と原本無変更。
- **2年度：2校×年2試合（計4試合）**、**5年度：2校×年3試合（計15試合）**のA方式スロット実測、ロスター・選手ID継続・キャッシュ全年度被覆・封印から翌年度の移行前検査・保存済み試合日付の照合。
- 予定外の日程を持つ試合の拒否。10000年v2日付トークンだけを保存して現行試合日時に入れない。

専用GitHub Actions`.github/workflows/career-calendar-v2.yml`は新規回帰テストと5年度A方式ベンチマークを実行し、実際のJSON成果を30日間保持。マージは全Python単体テスト・関東17校E2E・専用日付試験のすべて成功を必須とする。

## 残る課題

- 47都道府県の新年度日程・特別枠・予選免除・学校地区割、春秋夏の大会組み合わせを架空の内部年度ゲーム規則としていつから固定再利用できるかを決める必要がある。**2026公式の開催日は2027年以降の実際の開催日を保証しない。**
- 既存の`historical_matches.match_date`、日付別read model、GUI、試合ランタイムを`GameDaySlot`永続化方式へ改修する互換マイグレーションは未実施。v2日程DBは独立した架空テスト用記録。
- 10000年以降のゲーム進行は依然未実装。正式にゲームを「実質無制限の年度数」にするには暦とイベントの順序を統一し、ゲームセーブの全年度を通してコホート・学校・大会ルール・個人成績のID/整合性を守る必要がある。SQLite INTEGERは符号付き64bitで有限である。
- 3,000校×100年の実大会日程の生成・全国完全年次試合E2E、Windows正式GUI実機・保存容量監査も未検証。
