# Stage 43C-2：長期間進行中の試合日チェックポイントと履歴SQLite保護

作成日：2026-10-11

## 現状の再点検

- 実際のキャリア保存先には、既存の `HistoricalMatchArchive`（セーブスロット別の `historical_matches.sqlite3`）がある。
- 既存実装は、`(year, competition_id, match_id)` をキーにA方式の試合結果・イニング得点・打者投手GameStatsをイベント単位ログなしで保存し、同一結果の再保存を許容、変更結果を拒否する。
- 終了年度は`seal_year()`で件数と台帳ハッシュを確定、後年から変更不可。古いセーブを読み込んだ場合も、履歴DB内の試合は削除しない。
- `BrowseRepository`は別の閲覧用DB（年度単位の再構築API）であり、既存のキャリア履歴正本と混同しない。今回の追加修正で`BrowseRepository.replace_season_views`の一般契約は変更しない。

## 発見した穴

`LiveGameService.advance_to()` / `advance_through()` は、これまで複数日を一気にシミュレーションし、**最後に1回だけJSONセーブと履歴SQLite同期**していた。その途中でプログラムが終了すると、途中まで確定した試合は前回セーブに存在せず、再開時に巻き戻る可能性がある。

## 対応

`LiveGameService._advance_with_checkpoints()`で進行を日付単位に分割。自動保存が有効な場合：

1. 1日進めて新たに確定した試合件数を取得。
2. **新たな確定試合が1件以上ある日**には、従来の`save_game`を即時実行。JSONを先に書き、保存成功後に既存のappend-only履歴SQLiteへ同期。
3. 試合のない日は追加I/Oを避ける。目標日にも最終チェックポイントを残す（すでにその日時で保存済みなら重複を避ける）。
4. `advance_through`は目標日当日の試合実行後にも保存する。
5. `autosave=False`指定時は、従来通り**進行を保存しない**。暗黙にディスクへ保存しない。
6. 1日単位の`play_today`/`next_day`は従来通り自動保存可能なため変更しない。

## 中断・復旧の境界

- JSON書き込み失敗時には、その回の履歴SQLiteへの同期は起動しない。
- その時点より前に成功した日のチェックポイントは維持し、再読込後の決定的再実行で履歴DBを冪等同期できる。
- 1日に複数の試合がある場合は**試合単位でなく試合日単位**のチェックポイント。1日の途中でプロセス異常終了した場合、その日の未保存の試合は再実行対象となる。1試合ごとの厳密な書込境界は後続工程。
- 日付のない試合・スコアのみの`generated_v1`は、イニング／GameStatsを捏造せず従来方式で履歴保存する。
- 旧スロットの読み戻し、sealed年度への新規追記禁止、同一試合の改竄検知は既存の`HistoricalMatchArchive`に委ねる。

## テスト

`tests/test_stage43c2_incremental_checkpoint.py`

- 複数日ジャンプで確定日ごとにJSON→SQLiteの保存が進む。
- 2回目のJSON保存失敗でも1回目までの履歴が残り、後続の再同期で不足試合のみ追加。
- `advance_through`の目標日試合も最終保存に含まれる。
- 自動保存を明示的に無効化した時は副作用がない。
- 不正な年度・過去への日付指定で履歴を書き込まない。
