# Stage 43G-24：年数無制限に向けたゲーム年度座標・暦日付・セーブ継続境界

作成日：2026-10-11。前段 Stage43G-23 PR #164 は全4ジョブ成功で main マージ済み。

## 目的

長期履歴を50年/100年保存・閲覧できる基盤の次は、ユーザーの目標「**進められる年数に実質的な上限を置かない**」に向け、2026年を開始年度とした経過年・当年の日付・大会マスターの適用年を分離する。

現在の履歴SQLiteは年度`INTEGER`で保存し、翌年度登録の契約は「前年度がsealed、年度はちょうど+1」。ただし既存大会日程は2026年の現実の大会資料をもとにした固定日付であり、元試合`match_date`や年次進行の大部分は`YYYY-MM-DD`相当の暦日付を使用している。Python標準`datetime.date`は西暦9999年までしか表せない。単純に2026年の大会日程を毎年使い回したり、9999→10000をISO日付のまま処理するのは危険。

本Stageでは**セーブ構造・ゲーム大会エンジンを変更せずに、将来のゲーム年境界の契約と読み取り専用事前診断を実装**する。実際の年度進行上限を解除するものではない。

## 実装（`phase2_engine/career_era_calendar_contract.py`）

### 1. 保存キーの年度座標
- `career_coordinate(game_year, initial_year=2026)`：`game_year`（現行`career_years.year`等の値）と、開始年度からの`career_year_index`（2026→0、2075→49、2125→99）を返す。過去のセーブキーを書き換えない。
- 暦年に変換できる範囲を`gregorian_iso_year_supported`として示す。10000年度以上は`calendar_binding=requires_new_calendar_date_representation`。既存年度番号・年次進行がそのまま使えるという意味ではない。
- Python SQLiteの`INTEGER`が符号付き64bitであるため、物理DBの年度キーとして扱える上限は2^63−1。整数無制限の数学的保証を宣言しない（実用上の十分長い将来期間を想定）。

### 2. 日付の事前変換（正式大会日程ではない）
- `calendar_day_preflight(game_year,month,day,template_year=2026)`：対象の月日がテンプレートとして妥当か確認する。
- 9999年以下は標準Gregorian dateで`YYYY-MM-DD`候補を返すが、**競技大会日程を認定せず**`is_game_schedule_approved=false`を維持する。2026の大会日付を2027以降に公式日程として転写しない。
- 10000年以上はPython Gregorian日付を生成せず、`G10000:05-12`等の**設計上の論理日トークン**だけを返す。これは日付ではなく、元の`historical_matches.match_date`に入れてはいけない。
- 2/29はテンプレートと対象の閏年がともに合法な場合にだけ変換。10000年度以降の閏日については正式な暦規則がないため拒否する。

### 3. 前年度の読み取り専用封印・台帳検査
- `next_year_preflight(archive_path,requested_year)`：既存の`historical_matches.sqlite3`をSQLite URI `mode=ro`で開き、登録年度の連続性、最新年度がactiveかsealedか、最新封印台帳のゲーム行ハッシュ一覧の再計算を実施する。
- 前年度がsealed、要求年度がちょうど+1の場合にだけ`archive_year_registration_preflight_ok=true`を返す。これは**SQLite履歴登録の条件確認だけ**であり、`runtime_season_start_authorized=false`を維持する。
- 前年度active、1年以上のスキップ、過去年度、欠損DB、台帳不一致はそれぞれ理由を返すかエラーにする。バックアップ・セーブの改変や`CREATE TABLE`は実行しない。
- 9999→10000は`archive_year_registration_preflight_ok=true`となり得るが、`calendar_yyyy_supported=false`、`decision=archive_only_calendar_boundary_unresolved`と明示。実ゲーム進行の許可ではない。

### 使用例

```sh
python -m phase2_engine.career_era_calendar_contract --archive SAVE/historical_matches.sqlite3 --requested-year 2028 --month 5 --day 12
```

出力はJSON。ログイン中の実セーブには一切書き込まず、改修・移行は手動の後続実装が必要。

## 不変条件と長期移行に向けた設計判断

1. **試合原本はA方式を維持**（試合結果・イニング別得点・個人成績）。打席イベントは不要。封印年度の原本・台帳・学校/選手IDを変えない。
2. 学校マスター`school_id`・選手ID・大会IDは参照用の安定キー。年度またぎも既存の原本と紐づける。
3. **年度（game_year）と暦日付は別もの**と扱う。将来のISO表現から独立したDaySlotを正式に導入するなら、既存2026からの移行、月日/閏年、並び順、過去大会表示、開催日差・休養日・日付別閲覧などをテストしなければならない。
4. 2026年の正式大会日程・大会の特殊規則・予選免除条件・学校の地区所属を、そのまま2027年度以降の現実の事実として再利用しない。ゲーム内の**架空次年度**として固定ルールを承認する工程と、実際の2027公式日程を調査する工程を区別する必要がある。
5. 年度進行の正式手順は「前年度の完了判定→原本全試合封印→参照用統計キャッシュ生成（任意・派生）→新年度ロスター（卒業／入学）→新年度大会登録→翌年日程→試合結果と成績の永続保存」。この手順は本Stageではまだ原子的なランタイム動作になっていない。
6. バックアップ・増分セーブはアーカイブ元台帳、過去ロスター、元試合SHAを保持した状態で検証する。**キャッシュは再作成可能**。ゲームの未確定大会や新年度ロスターを省略したバックアップを復元可能と誤認しない。
